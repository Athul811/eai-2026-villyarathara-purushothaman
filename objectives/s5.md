## By the end of this session, you can

1. **Identify** the failure modes: network failure, partial processing, duplicate messages and poison messages.
2. **Explain** the unknown state. Tell why a timeout does not give you the result of the work.
3. **Apply** a dead letter channel. Give the difference between it and an invalid message channel.
4. **Apply** an idempotent receiver.
5. **Explain** the difference between compensation and rollback.
6. **Explain** the dual-write problem. Identify the transactional outbox as one answer.
7. **Apply** a correlation identifier. Give the difference between it and a message identifier.
8. **Relate** a reliability choice to a recovery time objective and a recovery point objective.

## The hard parts

These are the parts that people find difficult. Read them before the
session. If you cannot follow one of them, make it your question.

- **A timeout does not tell you the result.** The work possibly finished. The answer possibly disappeared. You must design for this third condition, and not only for success and failure.
- **Idempotency needs a key and a store.** It is not a result of careful code. You record the identifier of each message that you process. Then you compare each new message against that record.
- **A dead letter queue that nobody monitors is data loss with more steps.** The queue keeps the message. It does not tell you that the message is there.

## Self-check

Answer these before the session. They are not graded, and I do not
collect them. They show you which of the hard parts you cannot yet
explain. **A question that you cannot answer is your question for the
session.**

1. You send a payment request. You receive no answer before the timeout. Name the three possible states of the payment.
   <details><summary>Answer</summary>

   The payment did not start. The payment finished, and the answer disappeared. Or the payment is still in progress. You cannot tell them apart from outside, and you must not retry until the operation is idempotent.

   </details>

2. A message stops your consumer each time it arrives. What must happen to it?
   <details><summary>Answer</summary>

   After a set number of attempts, the consumer moves it to a dead letter queue. It must not block the queue, and it must not disappear. Somebody must then receive an alert about the dead letter queue depth.

   </details>

3. What is the difference between a correlation identifier and a message identifier?
   <details><summary>Answer</summary>

   A message identifier is unique for one message. A correlation identifier is the same for every message in one business transaction. You usually use the message identifier for idempotency, and the correlation identifier to follow a flow. When a consumer receives exactly one message for each order, the order's correlation identifier is also a good idempotency key. PA5 uses it in this way.

   </details>

## What the assignment will require

**PA5 — events, dead letter queues and idempotency**

You extend an order flow. You add retries, a dead letter queue, an invalid message channel, an idempotent consumer and a replay.
The message payloads use `canonical/order.schema.json` from PA4.
The assignment assumes that you can do these things:
- Declare an exchange, a queue and a dead letter exchange.
- Classify an error as permanent or temporary.
- Store the identifier of each processed order, and check it.
- Move a poison message out of the main queue.
- Replay a message from the dead letter queue.
