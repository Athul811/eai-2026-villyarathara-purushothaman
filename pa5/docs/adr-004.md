# ADR-004 - Header-carried correlation, three-attempt retry, file-backed idempotency and return-exchange replay

**Status:** accepted
**Date:** 2026-10-26

## Context

An order fans out over orders.exchange to payment, inventory and notification, and none of them is reliably up. Four things looked simple until a message actually failed.

The correlation id has to survive several hops: order-service, three consumers, three result queues, the DLQ and replay. The canonical order schema has additionalProperties: false, so the id cannot go in the body.

Failures need classifying. A simulated payment failure is temporary and is worth retrying. A body that is not JSON fails identically every time, so retrying it only delays the diagnosis by three attempts and then puts it in the DLQ.

Delivery is at-least-once, so notification-service can see the same order twice, for example after a replay or after an order is posted again with a new message id.

Replay has to send a message back to the consumer that failed it and to no one else.

## Decision

correlationId is a message header (msg.properties.headers.correlationId), generated with randomUUID() in order-service's POST /orders and never written into the order body. Each consumer copies it onto its result event.

Retry is the provided path. A failure calls nack(msg, false, false), so the broker dead-letters the message into the consumer's retry queue and it returns after the TTL. getRetryCount counts only "rejected" x-death entries. When the count reaches MAX_RETRIES - 1 (default 3 attempts), the consumer publishes to orders.dlq.exchange with an originQueue header and acks.

Classification happens in each consumer's catch block. A SyntaxError from JSON.parse, or a missing correlationId header, is permanent: the original bytes and headers go to orders.invalid.exchange, the message is acked, and there is no retry. JSON.parse sits inside the try so a bad body cannot crash the consumer.

notification-service keeps its processed ids in /data/processed-ids.json, re-read for every message and written through a temp file plus rename. It appends the log line first and records the id second.

POST /dlq/replay takes messages one at a time with channel.get, republishes the original bytes to orders.return.exchange with originQueue as the routing key, uses withoutRetryHistory(headers) so the retry count restarts, and acks only after republishing.

## Alternatives considered

AMQP's native properties.correlationId instead of a header. The provided DLQ publish copies only headers, so a value in properties would be silently lost on the way to the DLQ and again on replay. A header travels with the existing code unchanged.

An in-memory Set for idempotency. After docker compose restart notification-service the set is empty, so a redelivered or replayed order would be written to notification.log again and the customer notified twice. The file survives the restart.

nack with requeue=true. It skips the TTL delay completely, can loop forever, and never produces an x-death header, so the DLQ would never be reached.

Replaying through orders.exchange. The fanout would deliver the message to all three consumers, so inventory would process a payment failure's order a second time. The direct return exchange targets one queue.

Fewer or more attempts. At a 20% payment fail rate, three attempts all failing has probability 0.2^3 = 0.8%, which keeps the DLQ small without a long wait. More attempts would cut that further but delay everything that really is broken.

## Consequences

The retry window is only a few seconds. A downstream that is down for thirty seconds exhausts three attempts and lands in the DLQ, so a person has to trigger replay. Nothing downstream is told that an order is stuck: if payment succeeds and inventory stays down, the order just sits in orders.dlq.

Only notification-service is idempotent. A duplicate or a replay of a message that half-succeeded would make payment-service and inventory-service do their work twice.

The dedup file is read and rewritten whole for every message, which will not scale. It is also unsafe with two notification replicas: both could pass the check before either writes, and the second write could drop the first one's id.

Treating a missing correlationId as permanent keeps untraceable messages out of the retry path, but it means those messages land in orders.invalid, which has no replay. If that classification is too broad, real failures are parked there for good. If it is too narrow, retries are wasted.

order-service holds orders in memory by correlationId, so GET /orders/:id loses everything on a restart. A future consumer that forwards a message without copying the header breaks tracing from that hop onward.
