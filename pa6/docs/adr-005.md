# ADR-005 — Orchestrated checkout saga behind a contract-first API

**Status:** accepted
**Date:** 2026-11-03

## Context

POST /checkout has to turn one order into four downstream calls (payment, inventory, shipping, notification) and leave the system consistent when one of them fails partway. Three problems shaped the design:

- Only payment and inventory have undo endpoints. Shipping and notification do not, so a failure at step 4 can roll back money and stock but not the shipment that was already created.
- A downstream call can fail in two different ways: it refuses (a business failure) or it does not answer in time (the outcome is unknown, since the service may have processed the request). The contract maps these to 422 and 504.
- A retry or second request with the same Idempotency-Key can arrive while the first saga is still running. It needs its own answer (409 `idempotency_conflict`), not a hang or a second saga.

Writing openapi.yaml first forced me to decide the error shape (`ErrorResponse` with a `code` enum) and a bound on `items` (`maxItems: 100`) before writing code. I chose 100 as a round upper limit that is far above a realistic web or mobile order but still keeps the request size bounded. The Spectral rule against unbounded arrays forced me to pick a number instead of leaving it open, and I then enforced the same number in `server.ts` so the contract and the code agree.

## Decision

- **Strict sequencing.** The orchestrator loops over a plan of four steps with `await` inside the loop, so each call starts only after the previous one succeeded.
- **Timeout vs failure.** `callDownstream` uses an `AbortController` that fires after `REQUEST_TIMEOUT_MS`. Only an `AbortError` counts as a timeout (trace status `timeout`, HTTP 504). A non-2xx answer is a failure and takes the `code` from the service's JSON body, falling back to `<step>_failed`. Any other thrown error, such as connection refused, is `downstream_unreachable` and is treated as a 422 failure, not a 504.
- **Compensation.** Compensation runs in reverse order (`inventory_release`, then `payment_refund`) and only for steps recorded as completed, so a failed payment is never refunded. A failed undo does not stop the next one from being attempted. If any undo fails, the result is 422 `failed` with `compensation_failed`. Otherwise the result is 504 for a timeout and 422 for everything else, with status `compensated` if anything was rolled back and `failed` if payment itself failed.
- **Idempotency.** The store is read from disk on every request. The code checks the key and writes the `in_progress` claim with `readFileSync` and `writeFileSync` and no `await` in between, so two requests cannot both pass the check. That is what makes the claim atomic, and the claim being on disk is why a replay survives a container restart. Same key and same payload after completion returns the stored status and body. A different payload returns 409 `idempotency_payload_mismatch`.
- **Money.** Prices are summed as integer cents and formatted once at the end, never through `parseFloat`.
- **Bound enforced in code.** `MAX_ITEMS = 100` is checked in `server.ts` and returns 400 `validation_error`, matching `maxItems: 100` in the contract.
- **Unexpected errors.** The catch block deletes the idempotency record, so the key can be retried, and returns 500 `internal_error`. I first left this out of the contract. I added the 500 response and the enum value in a later commit once I saw the mismatch.

## Alternatives considered

- **Choreography, as in PA5.** Each service would react to an order event on its own. I rejected it because checkout needs one place that knows the whole outcome, a single synchronous answer for the caller, and a defined rollback order. With choreography I would lose that single answer and the strict ordering, and failure handling would be spread across services.
- **Parallel downstream calls.** Rejected because the steps depend on each other, and an early failure should stop later calls from starting. I would also lose a simple reverse-order rollback.
- **Compensating endpoints for shipping and notification.** This would remove the unrecoverable step, but the mock services are fixed and a real shipment or sent email cannot always be recalled. In a real system I would want this for shipping, for example a cancel-shipment call, because it would close the gap where a notification failure leaves a shipment behind. I did not do it here because the mock services are fixed, and some effects, like a sent notification, cannot be fully undone anyway.

## Consequences

Easier: the contract, the code and the status mapping agree, and every outcome has one HTTP status and one code. Adding a step means adding an entry to the plan and, if it has an undo, one compensation block.

Costs I accepted:

- **No saga recovery.** The `in_progress` claim is written before the saga runs, so a process killed mid-saga leaves a record that answers 409 `idempotency_conflict` for that key forever. The catch block only covers thrown errors, not a killed process.
- **Atomicity is single-process.** The claim relies on synchronous file I/O in one Node process. Two orchestrator instances sharing `/data`, or an `await` added before the claim, would reopen the race.
- **A timed-out compensation is ambiguous.** If a refund times out, I report `compensation_failed`, but the refund may have succeeded. There is no retry.
- **Notification failure leaves a shipment.** Money and stock are restored, but the shipment stays created.
- **The 500 path does not compensate.** After an unexpected error, the key is released without rolling back completed steps, so a retry reruns the saga from payment. I did not check how the payment mock handles a repeated `orderId`, so a retry could charge twice.
- **Same `orderId`, different keys.** Idempotency records are keyed by `Idempotency-Key` only, so two requests for the same order with different keys each run their own saga.
