# ADR-010 — Mark crashed sagas needs_attention and compensate only on operator command

**Status:** accepted
**Date:** 2026-11-20

## Context

The orchestrator keeps its sagas in memory and persists the whole store to /data/saga-store.json after changes, by writing saga-store.json.tmp and renaming it over the old file (orchestrator/server.js:23). A crash between two provider calls leaves a saga in a running state in that file while the providers have already done some of the work: a payment may be authorised, stock reserved, a shipment created. I killed cap-orchestrator during a slow shipping call and restarted it. After the restart, GET /sagas/stuck listed the order as needs_attention with completedSteps payment and inventory and an empty compensatedSteps, so the charge and the stock reservation were in place and shipping had not been recorded. I then called POST /sagas/:cid/compensate, which answered compensated, and /sagas/stuck was empty again. The delay was set through POST /admin/config on the shipping mock (delayMs 8000) and reset to 0 afterwards.

## Decision

On start, any saga found mid-flight is moved to needs_attention, and an order.needs_attention outcome is published (orchestrator/server.js:156-159). GET /sagas/stuck lists sagas in needs_attention or compensation_failed (line 289). POST /sagas/:cid/compensate works only for those two states and refuses others (line 302). It refunds the payment and releases the inventory, so a person decides it. Nothing resumes automatically.

## Alternatives considered

Automatic resume: on restart, replay each running saga from its last recorded step. Payment and inventory take an Idempotency-Key (authorize:<businessKey>, reserve:<businessKey>), so repeating those two calls would be safe. I rejected it because the store only records a step after its call returns, so after a crash I cannot tell whether the call in flight reached the provider, and shipping has no such key in my design. Resuming could create a second shipment. Marking the saga and handing it to an operator costs a person's time but never repeats a side effect. A second alternative, an outbox written in the same file write as the state change, would close the gap but needs a relay process I did not build.

## Consequences

The detection rule has false positives. A saga that finished at all providers but crashed before its completion was written is reported as needs_attention, and compensating it would refund a delivered order. So an operator must check the provider effects (GET /admin/effects on payment, inventory and shipping) before pressing compensate, as runbook.md says. The saga store is one JSON file rewritten in full on each persist, which is simple and survives a crash mid-write, but it becomes the first thing to break under ten times the load. Temporal would replace both the store and the restart sweep: its workflow history records each step, so a crashed worker resumes at the right step instead of marking the saga for a human.
