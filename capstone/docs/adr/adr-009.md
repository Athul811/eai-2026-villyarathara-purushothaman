# ADR-009 — A wire-tap trace of fire-and-forget hops

**Status:** accepted
**Date:** 2026-11-21

## Context

One order passes through intake, the orchestrator, four providers and the notifier. Four services' logs do not show the order of events for one correlationId, and a retry or a redelivery makes the log lines even harder to connect. An operator needs one ordered list of what happened to one order.

## Decision

Each service builds a hop (hopId, correlationId, causationId, service, operation, status, attempt, startedAt, finishedAt, durationMs, optional messageId and detail) with makeHop, and publishes it with emitHop to the trace.events exchange (intake/hops.js). The observer consumes the trace.store queue, drops a hop whose hopId it has already seen, appends it to /data/trace-store.jsonl and indexes it by correlationId (observer/server.js:13, 19-20, 42-47). GET /trace/:cid returns that order's hops sorted by startedAt (observer/server.js:89).

Causation: each hop carries the hopId of its parent as causationId. In the trace of order 0c8c94eb the chain runs intake.receive, intake.translate, intake.enrich, intake.publish, saga.consume, payment, inventory. The causationId also travels in a message header, so the orchestrator reads it from the incoming message (mkTrace(cid, h.causationId ?? null, retryCount(h) + 1, ...)). The attempt number comes from the retry count in x-death, because a nack cannot rewrite the headers. Work that no message started has a null causationId: in my kill test saga.stuck and saga.operator_compensate each began a new chain. A redelivery shows up as a skipped saga.dedupe hop with reason redelivery.

## Alternatives considered

Scatter-gather: the observer would ask every service for its records when someone requests a trace. Rejected because a service that is down or restarted cannot answer, which is exactly when a trace is needed.

OpenTelemetry: a standard SDK, collector and backend. Rejected because it would add a collector container and dependencies for something this small, and I could not justify them against the allow-list in the time available.

Confirmed publishing of hops: rejected because a trace problem would then slow down or fail an order. hops.js uses a separate non-confirm channel and swallows publish errors, so a lost hop never fails a business operation.

## Consequences

The trace can have gaps: if a service's trace channel is closed (hops.js sets it to null on close) or the broker is down, emitHop drops the hop silently and nobody is told. An incomplete trace is therefore not proof that a step did not happen. Sorting by startedAt uses each service's own clock, so two hops from different containers could be out of order by a few milliseconds, which is why causationId is the real ordering.
