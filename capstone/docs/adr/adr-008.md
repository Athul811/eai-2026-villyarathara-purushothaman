# ADR-008 — Three dedup layers: intake key, saga business key, provider keys

**Status:** accepted
**Date:** 2026-11-21

## Context

One order can become two in several places: a client repeats an HTTP request after a timeout, a customer submits the same order again, RabbitMQ redelivers a message after a crash, the orchestrator repeats a provider call after a retry, and the notifier receives the same outcome twice.

## Decision

Layer 1, the intake Idempotency-Key: intake refuses a POST /orders without a well-formed key (400 validation_error, intake/server.js:113-116), and the same key with the same body returns the same correlationId and publishes one event. It catches the client that sends the same request twice.

Layer 2, the saga business key source:orderId (orchestrator/server.js:88): the first correlationId seen for a business key is stored in store.businessKeys (line 220), and a later submission under another correlationId becomes state duplicate with duplicateOf (lines 210-218). I saw this: resubmitting the same fixture with a new Idempotency-Key returned state duplicate. The same layer handles redelivery of one message: a saga already in an outcome state republishes its stored outcome and skips the work (lines 200-203). I saw this too, as the saga.dedupe hop with reason redelivery after I restarted the orchestrator.

Layer 3, provider keys: orchestrator/server.js:113 sends Idempotency-Key on the calls that define one, authorize:<businessKey> for payment and reserve:<businessKey> for inventory. It catches the call repeated after a crash or retry that the first two layers cannot see.

Notices are at-least-once: the notifier checks a persisted set of processed correlationIds before sending and adds the id after the send succeeds (notifier/server.js:109, 118), so a crash between send and save sends the notice twice. A repeated notice is harmless, a repeated charge is not, so only the charge is made exactly-once in effect.

## Alternatives considered

One layer only: the intake key alone does not stop a customer who submits the same order with a new key, and the business key alone does not stop a provider from charging twice when the saga repeats a call.

Dedupe on the correlationId only: it is a fresh UUID for every submission, so it cannot recognise the same order submitted twice.

An idempotency key on the notification call: it would remove duplicate notices, but a persisted check in the notifier gives the same result without relying on the provider to honour a key.

## Consequences

The layers have a gap: the shipping request carries no Idempotency-Key (the shipping mock's effects log shows idempotencyKey null), so a repeated create call can make a second shipment. The business key is recorded when the saga starts (line 220) and I did not see it cleared for failed orders. The three stores are JSON files or in-memory sets rewritten on each change, which works at this size and would be the first thing to replace under much higher load.
