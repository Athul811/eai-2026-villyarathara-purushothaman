# ADR-007 — The saga starts from an order.accepted event and acks only when it is done

**Status:** accepted
**Date:** 2026-11-21

## Context

In PA6 the saga started from an HTTP request, so the caller and the orchestrator had to be up at the same moment and the caller waited for the saga. In the capstone, intake only normalises and publishes order.accepted and answers 202, and the orchestrator picks the event up from saga.queue when it is ready.

## Decision

The orchestrator consumes saga.queue with a prefetch equal to SAGA_CONCURRENCY (5), so at most five sagas are in flight and unacked. It acks a message when the saga reaches an outcome (orchestrator/server.js:203 for a repeated message, and the acks near the end of the handler). Until then the message stays unacked. I saw the effect: I killed the orchestrator during a slow shipping call, and after restart the same message came back as a second saga.consume hop, was recognised as a redelivery (saga.dedupe) and acked.

The state is saved to saga-store.json with the outcome (envelope and routing key) inside the saga, and the outcome event is published afterwards. If the process dies after saving the terminal state but before publishing, the message is unacked and is redelivered, and the dedupe branch republishes the stored outcome (lines 200-203), so the outcome is not lost.

## Alternatives considered

Acking on receipt: the queue would never redeliver, but a crash mid-saga would lose the order silently, and nothing would mark it as stuck. Rejected.

HTTP from intake to the orchestrator, as in PA6: simpler to read, but intake would depend on the orchestrator being up, and a slow saga would hold the client connection. Rejected.

An outbox written together with the state change: it would close the gap between saving the state and publishing the outcome. Rejected because it needs a relay process, and the redelivery path already covers that gap here.

## Consequences

An unacked message holds one of five slots for as long as the saga runs, so a slow provider can fill all five and let saga.queue grow, which is what the saga_consumer_lag alert measures. A crash leaves the message to be redelivered and the saga to be marked needs_attention instead of resumed (ADR-010). The saved state is one JSON file rewritten in full on every change, so it is the first thing to break under ten times the load.
