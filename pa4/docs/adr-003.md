# ADR-003 — Three source translators with pricing enrichment and an allowlist payment filter

**Status:** accepted
**Date:** 2026-10-12

## Context

The three sources describe the same order in incompatible ways. The web store nests the address under `customer.address`. The mobile app flattens everything into abbreviated fields, with a comma-separated address string, an epoch timestamp, and numeric currency (978/840/826) and status (1-4) codes. The B2B partner sends XML that declares `encoding="windows-1257"`, so the Latvian diacritics are only correct if the bytes are decoded as CP1257 rather than UTF-8 or latin1. Each source also uses a different product id format (`PROD-001`, `001`, `SKU-PROD-001`), which has to be normalized before calling the pricing API. The B2B file carries a decorative `<UnitListPrice>` in comma-decimal style that must not be used as the price.

Enrichment bit in two ways. The catalog price of PROD-013 is the number 4.5, and the canonical schema requires the string "4.50". The pricing API can also answer 404 for an unknown product or fail with 401/500, and the translators must return `{ order, warnings }` instead of throwing.

Filtering: every source carries payment data in a different shape (card number, IBAN), and the schema's `additionalProperties: false` means any leaked field fails validation.

Smaller problems: the project's `noUncheckedIndexedAccess` setting made array indexing return `string | undefined` and produced 15 typecheck errors, and my first patch script failed because Node on Windows resolved `/tmp` to `C:\tmp`.

## Decision

- **Translators:** `translateWeb`, `translateMobile` and `translateB2B` each parse their own format, map onto `CanonicalOrder`, and call shared helpers. The mobile address string is split on commas, taking country from the last part, postal code from the second-to-last and city from the third-to-last, with `?? ""` fallbacks. - **Product ids:** normalized to `PROD-XXX` per source (unchanged for web, prepend `PROD-` for mobile, strip `SKU-` for B2B).
- **Price as string:** `unitPrice` is a decimal string because a float loses information a currency needs. `toDecimalAmount` turns the API's number into a string with exactly two fraction digits, so 4.5 becomes "4.50". [CHECK: state the exact method, e.g. toFixed(2).] Price, currency and tax rate always come from the pricing API. No price is hardcoded and `<UnitListPrice>` is ignored.
- **Failures:** `enrichFromPricing` returns a result with status `ok`, `unknown_product` or an error status that includes the `httpStatus`. `enrichItems` calls it for every line in parallel. A line that cannot be priced is dropped and a warning is added (`UNKNOWN_PRODUCT` or `PRICING_API_ERROR`, with the product id). The order is still returned. [CHECK: confirm a network failure such as a refused connection is also caught and returned as an error status rather than thrown.]
- **Payment data:** each translator builds the canonical order field by field from the fields the schema allows. The card and IBAN fields are never read into the output, so an unknown field or XML element cannot leak through. ## Alternatives considered

- **Fail the whole order when one line cannot be priced.** This guarantees no order is ever incomplete, but one unknown product would block an otherwise valid order. I chose to drop the line and warn so the failure stays visible and the rest of the order flows through.
- **Store `unitPrice` as integer cents.** This avoids float formatting problems, but the schema fixes `unitPrice` as a decimal string, so it would need converting back anyway.
- **Delete payment fields from a copy of the source (denylist).** This is shorter, but a payment field I didn't know about would pass straight through. An allowlist fails safe.
- **Cache pricing responses.** This would cut API calls, but it risks stale prices, and the tests change prices at runtime and expect the output to follow.

## Consequences

- **Easier:** all three sources produce structurally identical output, and the payment filter is safe by construction.
- **Harder / cost accepted:** dropping a line means an order can silently be incomplete. Anyone consuming the output must check `warnings`, and the canonical schema has no way to mark a line as "unpriced", so the information lives outside the order. Calling the API once per line is simple but slow for large orders.
- **What breaks first:** if the schema gains a required field, every translator fails validation until each mapping is updated, because the allowlist copies only what it knows. A fourth source with a new product id format would pass through an unrecognized id unchanged and probably come back as `UNKNOWN_PRODUCT`. If the model had to outlive this course, I would add a schema version field, a way to represent partially priced or failed lines instead of dropping them, a proper money type, and a structured address instead of splitting a string.
