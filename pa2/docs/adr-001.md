# ADR-001 — Durable queue, publisher confirms, manual ack, and correlationId propagation for PA2 order publishing

**Status:** accepted
**Date:** 2026-09-23

## Context

Four decisions in this assignment each looked safe until the broker actually died.

Publishing with `X-Publish-Mode: fire-and-forget` sends messages with `persistent: false`
and returns a 202 without waiting for the broker to acknowledge anything. Demonstration (c)
made this concrete: five messages published this way, followed by `docker kill pa2-rabbitmq`
(a hard kill, no graceful shutdown), left the queue with none of them recovered after restart —
even though the HTTP client had already received 202 for all five. The default, confirmed mode
publishes with `persistent: true` and does not resolve the publish call — and therefore does not
return 202 — until the broker's confirm callback fires. The same test, run in this mode, showed
zero loss across the same kill-and-restart cycle.

A durable queue on its own is not enough without persistent messages. Demonstration (a)
published a single confirmed message, then ran a graceful `docker restart pa2-rabbitmq`
(SIGTERM, not SIGKILL) — queue depth went from 0 to 1 before the restart and stayed at 1
after it, confirming that `durable: true` on the queue plus `persistent: true` on the message
is what survives a restart, not either alone.

Manual ack matters for what happens while nothing is consuming. Demonstration (b) stopped
the consumer, published a batch, and watched queue depth rise by exactly the batch size —
proving messages are held, not dropped, while unacked. Restarting the consumer drained the
queue to zero with no loss, which only works because `handleMessage` acks after successfully
writing to `received.jsonl`, not before.

correlationId propagation has to survive three hops to mean anything: the `x-correlation-id`
HTTP header on the way in, the AMQP `correlationId` message property in transit, and the
`correlationId` field in each line of `received.jsonl` on the way out. It would be easy to
satisfy "the consumer logs the correlationId" without that value ever reaching the output
file — demonstration tests that check `received.jsonl` directly for matching correlationIds
close that gap.

## Decision

`connectProducerChannel` opens a confirm channel (`createConfirmChannel`, not a plain
channel) and asserts the queue with `{ durable: true }`.

`publishMessage` sets `persistent: options.mode === "confirmed"` — persistence is only ever
true in the default mode, false in fire-and-forget. In confirmed mode, the call wraps
`channel.publish()` in a promise that resolves only when the broker's ack callback fires;
the HTTP layer does not send 202 until that promise resolves, so a 202 under confirmed mode
is a real durability guarantee, not just "the client accepted the write."

`connectConsumerChannel` opens a plain channel against the same durable queue, with
`prefetch(1)` so the consumer only ever holds one unacked message at a time.

`handleMessage` reads `msg.properties.correlationId`, parses the JSON body, appends a record
to `received.jsonl`, and only then calls `channel.ack(msg)`. The ack happens after the
write completes, not before — a crash between receiving the message and finishing the write
leaves it unacked and therefore redelivered, at worst producing a duplicate line, never a
silent loss.

## Alternatives considered

The realistic alternative to the confirm-callback approach is using `channel.publish()`'s
synchronous boolean return value as the success signal instead. That return value only
indicates whether the channel's internal write buffer is under its high-water mark — it says
nothing about whether the broker has received or persisted the message. Code written this way
looks almost identical to confirmed-mode code at a glance: `channel.publish()` is called, a
truthy result comes back, and the caller moves on. But it behaves like fire-and-forget, because
it resolves before the broker has acknowledged anything. Demonstration (c) exists specifically
to catch this gap: fire-and-forget mode in this codebase already skips the confirm handshake,
and the kill-and-restart test shows exactly what that costs. Relying on the return value instead
of the confirm callback would silently reproduce the same failure while looking, at the call
site, like a careful implementation.

## Consequences

The main cost accepted here is throughput. `prefetch(1)` means the consumer processes exactly
one message at a time — there is no batching and no concurrent consumption. If the queue backs
up for an hour under load, recovery is bounded by however long each `handleMessage` call takes,
one message at a time; demonstration (b) shows this pattern working correctly (depth drains to
zero with no loss), but slowly and serially, not in a burst. A higher prefetch would improve
throughput but risks acking messages out of order relative to when they are durably written, or
losing several in-flight messages at once if the consumer process crashes mid-batch — which would
undermine the exact safety property demonstration (b) depends on. Running two consumer instances
against the same queue would split messages between them (RabbitMQ's normal competing-consumers
behavior), improving throughput, but `handleMessage`'s appends to `received.jsonl` were not
designed or tested for concurrent writers, so ordering guarantees on the output file would no
longer hold.
