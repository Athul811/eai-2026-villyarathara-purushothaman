# ADR-006 — Checkout saga as a Temporal workflow with activities

**Status:** accepted
**Date:** 2026-11-10

## Context

In PA6 the orchestrator itself carried the saga's state. Before the first downstream call it writes an `in_progress` record for the Idempotency-Key to `/data/idempotency-store.json`, and it clears or finalises that record only when the saga finishes or when the `catch` block runs. A process that is killed mid-saga never reaches either path. Reading the code, the record is left in state `in_progress`, and the next request with the same key gets 409 `idempotency_conflict`, forever. Nothing records which steps had completed, so nothing can finish the saga or compensate it. That is the problem this port addresses.

Three other things shaped the port:

- Retries are now a decision per failure. A 4xx from a mock (`payment_declined`, `inventory_unavailable`) is a refusal that will repeat, so it must not be retried. A 5xx or no answer is temporary.
- The crash test showed that an activity can run twice. I killed the worker while shipping was slow (2000 ms). The saga still finished `completed`, payment was authorized once, and the shipping mock received two `create` calls about 7 seconds apart. The shipping step in the trace took 18,754 ms, because the attempt that died had to time out first.
- Workflow code runs in a deterministic sandbox, so the PA6 code that did I/O and read the environment cannot live in the workflow. It had to move into activities.

## Decision

- **Boundary.** The workflow (`worker/src/workflows/checkout.ts`) contains only the saga logic: the amount arithmetic, the step order, the compensation order and the trace. All six HTTP calls are activities in `worker/src/activities/index.ts`, reached through `proxyActivities`. The workflow imports only types from `../activities`.
- **Permanent vs temporary failures.** The helper `post` in the activities file returns on 2xx. A 4xx throws `ApplicationFailure.nonRetryable(message, code)` with the `code` from the mock's JSON body. A 5xx or a network error throws `ApplicationFailure.retryable`. A slow call is not handled in the activity at all; `startToCloseTimeout` fails the attempt.
- **Retry policy.** `startToCloseTimeout` is 2500 ms (PA6's per-call budget), with at most 3 attempts, 200 ms initial interval and backoff coefficient 2. Without a policy Temporal retries forever. With it, a call that keeps timing out fails after about 8 seconds.
- **Failure mapping.** An activity that fails for good arrives as `ActivityFailure`. The helper `failureCode` maps a `TimeoutFailure` cause to `timeout` (HTTP 504) and an `ApplicationFailure` cause to its `type`, which is the mock's code (HTTP 422).
- **Compensation.** After a failure the workflow calls `releaseInventory` and then `refundPayment`, each only if its step completed, so a failed payment is never refunded. A failed undo does not stop the next one. If any undo fails, the result is `failed` with `compensation_failed`. Shipping and notification have no undo.
- **Trace.** The local function `run` produces one trace entry per step, not per attempt, with timestamps from `new Date()`, which is safe inside a workflow.
- **Money.** `toCents` and `computeAmount` are ported unchanged from PA6, so amounts are summed in integer cents.
- **Return value.** The workflow returns a `CheckoutResult` for every outcome and never throws.

## Alternatives considered

- **Keep the PA6 orchestrator and add a recovery job that finishes stuck sagas on startup.** This is the real alternative. It would need the orchestrator to persist, after every step, which steps completed and with what result, so that a restart can resume or compensate. It would also have to cope with the call that was in flight at the crash, which may have reached the service. That amounts to writing a small workflow engine with its own history store. I rejected it because the engine already provides the history, resume and timers, and its behaviour is easier to inspect in the UI.
- **Retry every failure and let compensation sort it out.** Rejected. A declined payment would be tried three times, and the public test counts attempts. A refusal will repeat, so retrying only adds delay and load.
- **One activity for the whole saga.** Rejected. Step results would not be in the history, so a crash mid-saga would redo every step, and per-step retry and timeout would be lost.

## Consequences

Easier: a killed worker no longer strands a saga. The workflow resumes from the recorded history and does not repeat completed steps, and every attempt and failure is visible in the Temporal UI.

Costs I accepted:

- **Activities run at least once, not exactly once.** No engine can make this exactly-once, because when a worker dies after sending a request the engine cannot know whether the service acted on it. The shipping call proved it by reaching the mock twice. If `authorizePayment` were the step in flight, the customer could be charged twice unless the payment call were idempotent, for example by sending the `orderId` as an idempotency key. The mocks do not guarantee that, so this remains open for payment.
- **Redeploying a changed workflow is risky.** Running workflows are replayed against the new code. If the step order or the activities called change, replay can fail on non-determinism. Changes to a live workflow need versioning, which PA6 never needed.
- **More to operate.** The Temporal server, its history store, the worker and the api are now running parts, in place of one orchestrator with two JSON files.
- **Slower failure path.** A call that times out is tried three times before the workflow sees it fail, so a slow service costs about 8 seconds instead of 2.5 seconds.

## What the engine took over

- Timeouts: PA6 wrapped every call in an `AbortController` and turned `AbortError` into `timeout` by hand in `callDownstream`. In PA7 the activity's `startToCloseTimeout` does it, and the workflow sees a `TimeoutFailure`.
- Retries: PA6 had no retry loop at all, so one slow call failed the saga immediately. In PA7 the retry policy on `proxyActivities` retries temporary failures up to 3 times with backoff, and `ApplicationFailure.nonRetryable` stops retries for refusals.
- Idempotency record and atomic claim: PA6 read the store, checked the key and wrote `in_progress` with no `await` in between, in the checkout handler. In PA7 the api starts the workflow with the Idempotency-Key as its workflow id, and Temporal refuses a second workflow with the same id.
- Which steps completed: PA6 held this in the `completed` array in memory, so a crash lost it. In PA7 the workflow history records every activity result, and a restarted worker replays it to continue from the right step.
- Durability of the in-progress state: PA6 persisted it in `idempotency-store.json` and `saga-store.json`. In PA7 Temporal is the source of truth, and the api's files are only an audit mirror.
