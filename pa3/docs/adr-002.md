# ADR-002 — Idle-timeout aggregation with index-keyed deduplication for split order processing

**Status:** accepted
**Date:** 2026-09-30

## Context

Splitting one order into N independent item messages, routed to three different queues
(`orders.physical`, `orders.digital`, `orders.subscription`), breaks the natural ordering and
grouping an order previously had. Correlation has to be re-established entirely from message
content: `router-service` stamps every item message with the same `correlationId` (itself just
`orderId`) and the same `totalItems`, so the aggregator can later recognize which items belong
to the same order and know how many it's waiting for — without ever seeing the original order
object again.

The timeout mechanism itself is given (an idle timeout, reset on each result received, exposed
as `AGGREGATOR_IDLE_TIMEOUT_SECONDS`), but the actual number is an open decision with a real
trade-off. Too short, and a single slow item (a physical item with real fulfillment latency)
trips a false partial on an order that was still genuinely in progress. Too long, and "partial"
stops being a useful signal — callers waiting on `orders.complete` wait just as long for a
partial as they would have for a real completion, defeating the purpose of timing out at all.

A "partial" result also needed to be more than a flag. A caller receiving `status: "partial"`
with no further detail can't act on it — it can't retry specific items, can't tell a customer
which part of their order is delayed, and can't distinguish "9 of 10 items arrived" from "none
did." The missing-items detail needed to be explicit, not implied.

Finally, duplicate item results are a real, expected case, not an edge case to ignore: any
worker that acks late relative to RabbitMQ's redelivery timing will cause the same item result
to arrive twice. Counting it twice would corrupt `receivedItems`.

## Decision

`router-service.route_order` stamps every item message with `correlationId` (equal to
`orderId`) and `totalItems` (the full item count of the original order), identically across
every item regardless of which queue it's routed to. The original `orders.incoming` message is
acked only after every item has been published — not per item — so a crash partway through
publishing leaves the whole order unacked and redelivered, rather than partially routed.

`aggregator-service.aggregate_result` keys each order's `results` dict by `item_index`, not by
a list append. A redelivered duplicate for an already-seen index overwrites the same dict key,
so `len(order['results'])` always reflects the count of **distinct** items received, regardless
of how many times any individual item result was redelivered.

The timeout is measured from `last_activity`, updated on every result received for that order —
not from when the order first arrived. `sweep_timeouts` runs on a 1-second interval and compares
`now - order['last_activity']` against `IDLE_TIMEOUT_SECONDS` (default 5, from
`AGGREGATOR_IDLE_TIMEOUT_SECONDS`). In production I would run this closer to 15-20 seconds: the
test environment's 5-second value is deliberately short so the test suite doesn't take minutes
per timeout case, but a real physical-item worker doing real fulfillment work could plausibly
take longer than 5 idle seconds between legitimate results even while making genuine progress.
I'd pick the value by measuring p99 single-item processing latency across all three worker
types and setting the timeout at several multiples of that, so an order only times out when it's
actually stuck, not merely slow.

`_build_message` computes `missingItemIndexes` as `sorted(all_indexes - received_indexes)` for
both "complete" and "partial" statuses, using the same code path. A partial result therefore
always names exactly which `itemIndex` values never reported — never just a bare status flag —
giving a caller enough information to act on it rather than just knowing something's wrong.

`aggregate_result` acks every message unconditionally, including ones that fail to parse
(wrapped in a `try/except` around the initial `json.loads` and key access) — a single malformed
result is dropped and logged, not retried forever and not left blocking the queue.

## Alternatives considered

A fixed deadline measured from order arrival (`order_arrived_at + IDLE_TIMEOUT_SECONDS`)
instead of an idle timeout measured from last activity was the real alternative, and it's worse
specifically because it doesn't distinguish "stuck" from "slow but progressing." An order with
many items, where workers are still actively and correctly reporting results one at a time,
would still get killed and marked partial the moment a fixed wall-clock deadline from creation
elapsed — even though every item was arriving on schedule and the system was working exactly as
designed. The idle-timeout approach means an order with legitimately more items, or workers
with higher real latency, can run arbitrarily long as long as results keep arriving; only an
actual stall — silence past the threshold — triggers a partial. The trade-off is that a
genuinely abandoned order (one worker crashed before ever reporting, with every other item
already in) could in principle restart its own idle clock indefinitely if other, unrelated
late-arriving results for the same order kept trickling in — though in practice this assignment's
workers each handle their item once, so this is a theoretical cost rather than an observed one.

## Consequences

The aggregator's entire `in_flight` state lives in an in-process Python dict (`in_flight = {}`),
protected by a single `threading.Lock()`, with nothing persisted outside the process. If the
aggregator container crashes or restarts mid-order, every order currently being tracked loses
all of its accumulated state — including results that were already acked off `orders.results`.
Because `aggregate_result` acks unconditionally per message, those results are never redelivered
either; the data is simply gone, and no partial or complete message is ever published for that
order. This is the direct cost of keeping the "ack regardless, so one bad message can't jam the
queue" simplicity: it protects against malformed individual messages but not against the
aggregator process itself dying. At ten times the current traffic, or with orders carrying
hundreds of items instead of a handful, this same single-process, single-lock design would also
become a throughput bottleneck — every result for every concurrent order serializes through one
lock, and the 1-second sweep interval means a worst case of nearly a full second of extra latency
before a timed-out order is even noticed. Moving `in_flight` state to Redis (or another store
external to the aggregator process) would fix the crash-durability problem and allow horizontal
scaling of the aggregator itself, at the cost of a network round-trip on every single result
instead of an in-memory dict access.
